- 2026-08-24 support-plus-inline-purchase (SPEC 02): on-device visual verification caught a bug that deterministic review, semantic review, and an independent critic all missed — `TooltipBox` (Compose Material3) does not propagate a `BoxScope.align()` modifier passed via its own `modifier` parameter to its rendered position, unlike an ordinary composable (`Box`, `Icon`, etc.). `SupportPlusInfoIcon(modifier = Modifier.align(Alignment.TopEnd))` compiled clean and every code-level review approved it, but the icon rendered at the card's top-LEFT corner on the actual device. Root cause took ~40 min of dead-end debugging (build-cache paranoia, javap bytecode inspection of the wrong nested lambda class, RTL-locale theory) before a direct empirical test — swapping in a plain colored `Box` with the identical `.align()` modifier at the same call site — proved the modifier itself worked fine and isolated the fault to `TooltipBox` specifically. Fix: wrap the `TooltipBox`-returning composable in its own `Box(modifier = Modifier.align(...))` at the call site instead of threading the align modifier through the child composable's own `modifier` parameter. Lesson: for ANY Compose component that isn't a raw layout primitive (Box/Row/Column) — especially first-use library components like `TooltipBox`, `Popup`-backed composables, or anything from an unfamiliar API surface — do not assume a `BoxScope.align()` (or `weight()`, or similar scope-modifier) passed into its `modifier` param will actually position it; the fastest confirmation is swapping in a trivial colored `Box` with the identical modifier at the same call site, not staring at bytecode or theorizing about RTL/caching. This also reconfirms the standing rule that on-device visual verification is not optional for visual-surface SPECs — every review layer that only reads source code missed this.
